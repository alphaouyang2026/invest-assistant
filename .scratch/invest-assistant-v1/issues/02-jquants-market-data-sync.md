# 02 — J-Quants 行情同步与数据页

**What to build:** 用户在 `.env` 填好 J-Quants Light 的 API key，就能在数据页一键回填过去 5 年的日线行情、上市名册、交易日历和 TOPIX；之后每个开市日 18:00 自动同步当天数据。数据页显示数据到哪一天、同步进度、最近任务结果和质量警告。中断后重跑同步，结果与一次跑完相同。

**Design:** [invest-assistant v1 系统设计](../spec.md) §3.1–§3.4、§4、§8、§9（数据页部分）、附录 A.1 与 A.5

**Blocked by:** 01 — 项目骨架与运行环境

## Comments

**2026-09-23** — 除最后一项（用真实 key 回填）外都已完成。根目录 `.env` 里的 `JQUANTS_API_KEY` 目前是空的，填上以后执行 `docker compose exec backend uv run python -m app.cli sync` 即可完成那一项。

测试：后端 79 个、前端 4 个，都不访问网络。Docker 里已确认：启动时迁移建好 4 张表，`/api/*` 经前端转发可以访问，数据页能打开；没有 key 时点「立即同步」，任务记为失败，并提示去设置 `JQUANTS_API_KEY`。

与设计写法不同、或设计没写到而由我定下的地方：

- **拆合股核对的误差门槛**：设计写「相对误差超过 0.1% **或**绝对误差超过 0.1 日元就记警告」。J-Quants 的复权价只保留 1 位小数，50 日元以下的股票光是四舍五入就会超过 0.1%，所以改成**两个门槛都超过**才记警告。测试里有一只 43 日元的例子。
- **回填只抽样核对**：每日同步会核对本次出现调整系数的全部证券；回填（库为空时开始的那次）只随机抽 20 只，否则五年里几百只有拆合股的证券要逐只发请求。已知的遗漏：如果回填中途中断，重跑的那一次不再算回填，会把剩余区间里出现的全部拆合股都核对一遍，请求会多一些，但结果正确。
- **`var/jobs.jsonl` 由任务模块写**，不由 `sync` 写：服务里的任务和命令行都经过它，所以每次同步都只记一次。因此 `overview()` 不含「最近任务结果」，`GET /api/data/status` 同时调用 `overview()` 和 `Jobs.history()`。
- **OHLC 任一缺失都算 `untradable`**：设计表格只写了「`close` 为空」，但「价格齐全但成交量为空 → `excluded`」这句意味着价格不齐更糟。
- **`MarketData` 构造参数**：传 SQLAlchemy `Engine`（不是 session factory），另有两个只给测试用的关键字参数：`today`（今天的日期）和 `rng`（抽样用的随机数）。
- **`read(None, …)` 只返回股票**；要 TOPIX 需写 `read(["TOPIX"], …)`。
- **TOPIX 从它自己的最大日期之后接着取**，而不是只取本次同步的日期范围。这是「中断后重跑」测试逼出来的：中断前已提交的那几天，重跑时不会再取一次。
- **过去的开市日日线为空时，名册照常写入**，只对日线记警告。
- **同一类任务不重复排队**：已经有同步在排队或运行时再提交，返回的是那个任务的编号（连点两次「立即同步」，或 18:00 定时器撞上手动同步，都只跑一次）。
- **假适配器不模拟 429 和分页**：这两件事只发生在 HTTP 那一层，所以放在 HTTP 适配器的测试里，用模拟网络的 `httpx.MockTransport` 测；内存假适配器负责空响应和中途失败。
- **定时器的重试**：以上一次同步**结束**的时间加 30 分钟为准；只有「当天数据未出」会触发重试，别的失败不会自动重试。
- 前端的 `/api` 由 `next.config.ts` 转发到后端（容器里是 `BACKEND_URL=http://backend:8000`），浏览器只访问 3000 端口，不需要处理跨域。客户端用 `openapi-fetch` 加生成的 `schema.d.ts`。
- `read` 还没有做日历对齐（补齐缺失的日子），等 03 的策略真正需要时再按需求补上。

# 05 候选策略研究：Golden Path

> 状态：产品流程草案，用于 05 实现前评审；不表示策略已经有效。  
> 对应任务：[05 — 三类 OHLCV 策略候选研究](issues/05-three-ohclv-strategy-candidates.md)  
> Mock 页面：开发环境 `/accounts/research/prototype-candidates?variant=A`

## 1. 用户目标

05 不是让用户从三个策略里直接选择一个开始交易，而是让研究者回答：

> 一个规则已经冻结的候选策略，是否有足够、可复现且包含成本的样本外证据，值得进入模拟交易观察？

成功路径从研究草稿开始，以三种可审计结论之一结束：

- `passed`：满足预先声明的门槛，可以申请成为 paper challenger；
- `failed`：未满足门槛，保留失败证据，不进入模拟交易；
- `insufficient_evidence`：样本、成交或市场形势覆盖不足，不把未知当成通过或失败。

即使结论是 `passed`，也必须由用户人工确认，系统不会自动替换 champion。

## 2. Golden path 总览

```text
建立研究草稿
  → 运行前检查
  → 冻结并运行开发期
  → 版本化调整候选
  → 选择一个版本进入验证期
  → 查看锁定版本的验证证据
  → 决定是否开启一次性盲测
  → 得到通过／失败／证据不足
  → 人工晋级为 paper challenger
```

Golden path 默认研究一个策略家族。比较三个家族时，分别建立三份实验，避免在同一个表单里形成没有审计记录的参数笛卡尔积。

## 3. 阶段和用户操作

### 阶段一：建立研究草稿

用户从“策略研究”进入“新建候选研究”，选择一个策略家族和预注册版本：

- 长趋势：`long_trend_sma200_v1`，可选预注册变体 `absolute_momentum_12m_v1`；
- 短期反转：`short_reversal_5d_v1`，可选预注册变体 `short_reversal_20d_v1`；
- 横截面动量：`cross_sectional_momentum_6_1_v1`，可选预注册变体 `cross_sectional_momentum_12_1_v1`。

用户确认以下研究契约：

- 股票池、信号时点和预热规则；
- 排名／准入参数、持有期和再平衡频率；
- PeriodicTopN、等权、持仓数和现金限制；
- 次日开盘成交、ADV20 上限、拒单／部分成交规则；
- 基础成本以及 10／25／50 bps 压力情景；
- 开发、验证和盲测日期；
- TOPIX、股票池等权和 `technical_rating_v1` 基准；
- 主要指标、最低交易数和晋级硬门槛；
- TOPIX 市场形势是 `diagnostic_only`，还是作为有版本的交易 gate。

默认选择 `diagnostic_only`：形势只用于报告分组，不改变订单。

此时所有参数可编辑，用户尚未看到任何收益。

### 阶段二：运行前检查

用户点击“检查并冻结开发方案”。系统在运行收益回测前检查：

- 日期范围和预热行情是否完整；
- 股票池覆盖和可参与排名的证券数；
- 参数是否合法、规则之间是否矛盾；
- 计划持仓是否明显超过 ADV20 容量；
- 数据 manifest、代码 commit 和策略版本是否能够绑定；
- 验证期及盲测期是否仍未揭示。

检查失败时，用户返回草稿修正并重新检查。因为尚未查看收益，这不算结果驱动调参。

检查通过后，系统生成实验 ID、配置指纹和开发版本 `v1`。

### 阶段三：开发期与版本化调整

用户运行开发期并查看：

- 信号覆盖、候选数和成交数；
- 毛收益、成本后收益、回撤和换手；
- 容量拒单、订单／ADV20 和缺失数据；
- 分年与 TOPIX 市场形势诊断；
- 参数邻域和延迟一天成交压力结果。

开发期允许调整参数，但每次调整必须创建新版本，旧版本和失败结果不得覆盖。例如：

```text
short_reversal_5d_v1 · experiment version 1
  └─ 开发期发现 50 bps 成本后为负
short_reversal_20d_v1 · experiment version 2
  └─ 降低换手，成为验证候选
```

界面必须同时显示试验次数和版本谱系，不能只留下当前最好的一次。

用户从已有开发版本中选择一个，点击“锁定此版本进入验证”。

### 阶段四：锁定验证

进入验证前，系统再次展示即将锁定的完整契约。用户确认后：

- 策略、股票池、allocator、execution 和成本情景锁定；
- 验证期、盲测期和通过门槛锁定；
- 验证结果第一次被揭示；
- 同一候选不能再通过修改参数反复运行该验证区间。

验证报告显示：

- 总体、逐年和逐 fold 结果；
- TOPIX 与股票池等权的净超额收益；
- 回撤、Sharpe、Sortino、换手和成交率；
- 10／25／50 bps 后结果；
- 延迟成交、去除最好交易等稳健性测试；
- `策略版本 × 样本阶段 × TOPIX 形势` 证据矩阵。

形势矩阵中的每格必须显示覆盖交易日、区间数和成交数。样本不足显示 `insufficient_evidence`，不显示绿色“适用”。

验证结果出来后，用户不能再调整正式候选。若坚持修改，必须结束当前候选、创建新版本并退回开发阶段；已经看过的验证区间不能再称为严格 OOS。

### 阶段五：决定是否开启盲测

只有满足以下条件，页面才允许“开启最终盲测”：

- 验证硬门槛全部通过；
- 没有未处理的数据或执行警告；
- 最低交易数和股票池覆盖充足；
- 候选版本和全部配置已锁定；
- 盲测区间尚未揭示；
- 用户确认盲测对该版本只运行一次。

用户有两个正常选择：

1. 开启盲测；
2. 停止研究并保留验证结论。

此阶段不能调整参数、日期、成本或通过门槛。图表筛选和排序仍可改变，因为它们不改变研究事实。

### 阶段六：最终结论与人工晋级

盲测结束后，系统根据预注册门槛产生：

- `passed`；
- `failed`；
- `insufficient_evidence`。

报告必须给出结构化原因，例如：

- “50 bps 成本下净超额收益为负”；
- “收益集中于最好三笔交易”；
- “下跌高波动只有一个区间，不能判断”；
- “订单多次超过 ADV20 上限”。

`passed` 只解锁“申请晋级为 Paper Challenger”。用户在最终确认页查看冻结配置、起始日和与 champion 的关系，人工创建一个独立模拟账户。系统不自动替换 champion，也不删除失败候选。

## 4. 参数编辑规则

| 阶段 | 策略／组合／执行参数 | 日期和门槛 | 纯展示筛选 |
|---|---|---|---|
| 草稿 | 可编辑 | 可编辑 | 可编辑 |
| 运行前检查 | 可修正，之后重新冻结 | 可修正 | 可编辑 |
| 开发期 | 可调整，但创建新版本 | 原则上不改；修改建立新实验 | 可编辑 |
| 验证候选锁定前 | 只能从已有版本中选择 | 不可改 | 可编辑 |
| 验证结果揭示后 | 不可改 | 不可改 | 可编辑 |
| 盲测决策及之后 | 不可改 | 不可改 | 可编辑 |

特殊规则：

- TOPIX 形势用于报告分组时属于展示／诊断；改成 `gate_new_entries` 或 `force_exit` 属于策略变更。
- 临时追加的成本情景可标为 `exploratory`，但不能替换正式门槛使用的冻结情景。
- 修改规则、参数或成交语义必须产生新策略／实验版本；修改显示方式不产生版本。

## 5. 页面必须让用户始终看见的状态

无论采用哪种界面布局，页面都必须持续展示：

- 当前阶段以及下一道不可逆的门；
- 当前策略版本和父版本；
- 已运行的试验数，包括失败版本；
- 哪些样本已经揭示，哪些仍然封存；
- 当前可编辑字段与锁定字段；
- 市场形势是诊断还是交易 gate；
- 成本、容量、allocator 和 execution 摘要；
- 下一主操作及其后果。

“查看验证”“开启盲测”和“晋级 challenger”必须是三个独立动作，不能合并成一次“运行并使用最佳策略”。

## 6. 04 与 05 的衔接

04 提供实际逐日 SimulationEngine、输入指纹、指定区间运行和 TOPIX 形势区间。05 复用这些能力并增加研究治理：

- 全期连续运行以及按当日形势归因；
- 开发／验证／盲测阶段；
- 策略和实验版本谱系；
- 月度再平衡及横截面组合；
- 成本、容量和稳健性情景；
- 最终结论和人工晋级。

04b-B 的独立区间空仓启动继续作为外部场景实验，不替代全期连续 OOS，也不自动成为实时市场 gate。

## 7. Mock 的评审问题

开发环境 mock 提供三个结构不同的方案：

- `variant=A`：逐步向导——适合第一次做策略研究，强调当前任务和锁定摘要；
- `variant=B`：实验流水线——强调版本谱系、失败记录和每道 gate；
- `variant=C`：证据驾驶舱——强调多策略比较和证据矩阵，面向熟悉研究流程的用户。

评审时重点回答：

1. 用户能否一眼判断当前哪些参数还可以改？
2. 用户能否理解“开发版本”“验证候选”和“paper challenger”的区别？
3. 一次性盲测是否足够醒目且不容易误触？
4. 市场形势诊断是否会被误解成自动择时？
5. 失败版本是否仍然可见？

Mock 只使用内存中的示例数据，不调用研究 API，不创建数据库记录，也不代表 05 后端已经实现。
